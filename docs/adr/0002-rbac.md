# ADR 0002 — Roles and permissions

- **Status:** Accepted
- **Date:** 2026-10-08
- **Phase:** 1

## Context

The spec locks `spatie/laravel-permission` in teams mode (team = tenant) if it supports Laravel 13, and asks for
custom roles, granular module-registered permissions (`crm.leads.edit`), scoped access (own / department / branch /
all), and one extra rule: a permission is only effective if the tenant holds the entitlement for its module.

Checked on Packagist before installing: `spatie/laravel-permission` 8.3 supports Laravel 13 (MIT).

One part of the package does not scale with the tenant count: its check path loads **every** permission with
**every** role of **every** team into a single cache entry and unserialises it on each request.

## Decision

Keep the package for the schema and the assignment API; route every authorization decision through our own checker.

| Concern | Provided by |
|---|---|
| Tables, teams mode, `assignRole()` / `syncRoles()` | Package (`config/permission.php`, `teams => true`, team key `tenant_id`) |
| Permission checks | Ours: `Gate::before` in `App\Core\CoreServiceProvider` → `Access\AccessChecker` → `Access\PermissionResolver` |
| Permission catalogue | Declared in module manifests, written to `permissions` by `php artisan permissions:sync` |
| Role editing rules | Ours: `Access\RoleManager` |

Schema changes to the package stub (`2026_10_01_000030_create_permission_tables.php`): ULID `roles.id`,
`model_id` and `tenant_id`; `permissions.module`; `roles.description` and `roles.is_system`;
`role_has_permissions.scope` (`own` / `department` / `branch` / `all`).

`register_permission_check_method` is **off**, so the package's registrar is never asked. `PermissionResolver` runs
one indexed query per tenant + user and caches the result in the tenant's own cache namespace (10 minutes,
invalidated by a version counter).

`AccessChecker` is also where "no entitlement, no permission" is enforced: tenant active → permission registered →
tenant entitled to the module → user is an active member → owner or a role grants it.

`Role` deliberately has **no** automatic tenant global scope: the package loads roles through its own queries and a
scope there would leak one tenant's view into its shared cache. Isolation is explicit: `Role::forCurrentTenant()`,
`Role::resolveRouteBinding()`, and the `tenant_id` filters in `PermissionResolver`.

Rules: nobody can grant or remove a permission they do not hold; nobody can change, suspend or remove a member
who holds a permission they lack (`MemberManager`); a role can carry only permissions of modules the tenant is
entitled to; the Owner role is never assignable and never editable. The owner is implicit —
`tenant_memberships.is_owner` — so the Owner role has no grants in the database.

## Consequences

- Authorization cost stays flat as tenants are added, and entitlement is checked in exactly one place.
- **Do not call the package's check API** (`hasPermissionTo()`, `hasAnyPermission()`, the `role:` and
  `permission:` middleware, `@role`): it loads the platform-wide map and skips the entitlement check. Use the
  `can:{permission}` middleware, `$user->can()`, `Gate` or `AccessChecker`.
- Every `Role` query has to be scoped by hand. A missing `forCurrentTenant()` is a cross-tenant read.
- `Gate::before` returns a boolean for every registered permission, so no policy can grant what the checker denied.
  Abilities that are not module permissions fall through to ordinary gates and policies.
- After any change to roles, grants or assignments call `RoleManager::flush()`.
- A new permission does nothing until `permissions:sync` has run; `RoleManager` throws if the catalogue is stale.
- Scopes are stored but not evaluated yet: `RoleManager::syncPermissions()` writes every grant as `all`, and
  `department` / `branch` need the Phase 2 structures. `AccessChecker::scopeFor()` already returns the scope for
  policies to use.
- Platform users are outside all of this: `platform.*` abilities are answered by `Platform\Enums\PlatformRole`.
